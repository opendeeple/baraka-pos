# Deploying BarakaPOS (free-tier)

This covers the server (`server/`) + database. Desktop distribution (`client/`) already publishes via GitHub Releases (`electron-updater`) — see the last section.

## What you're setting up

| Piece | Service | Config in this repo |
|---|---|---|
| Postgres database | Supabase (free) | `server/.env` `DATABASE_URL` |
| API + Socket.io server | Render (free) | `render.yaml` |
| Keep both awake | GitHub Actions (free) | `.github/workflows/keep-alive.yml` |

## 1. Supabase — database

1. Create a free account at supabase.com and a new project (region close to your store).
2. Wait for provisioning, then go to **Project Settings > Database > Connection string > URI**.
3. Copy the **direct connection** string (port `5432`, *not* the pooler string on `6543` — see the comment in `server/.env.example` for why).
4. It looks like `postgresql://postgres:[YOUR-PASSWORD]@db.xxxxxxxx.supabase.co:5432/postgres` — replace `[YOUR-PASSWORD]` with the DB password you set during project creation.
5. Keep this string handy for step 3 below — don't commit it anywhere.

**The 7-day auto-pause**: a free Supabase project pauses if it gets zero database traffic for 7 days straight. The keep-alive workflow (step 4) prevents this by hitting your server's `/api/health` regularly, which keeps Prisma's connection warm — as long as the workflow is running, this won't trigger. If it ever does pause (e.g. you paused the GitHub Actions workflow), just log into the Supabase dashboard and click "Restore project."

## 2. Push this repo to GitHub

Render deploys from a GitHub (or GitLab/Bitbucket) repo. If this project isn't on GitHub yet:

```bash
git init
git add .
git commit -m "Initial commit"
gh repo create <your-org-or-username>/baraka-pos --private --source=. --push
```

(Ask me to run this for you if you'd like — I have `gh` available and authenticated, but creating/pushing to a real repo is the kind of action I won't do without you explicitly saying so.)

## 3. Render — server

1. Create a free account at render.com and connect your GitHub account.
2. **New > Blueprint**, pick the repo you just pushed — Render will read `render.yaml` at the repo root and propose the `barakapos-server` web service.
3. Before the first deploy, or right after (Environment tab), set the two secrets `render.yaml` intentionally leaves blank:
   - `DATABASE_URL` — the Supabase connection string from step 1.
   - `CORS_ORIGIN` — leave as-is (`http://localhost:5173`) unless you build a browser-based client later; it doesn't affect the desktop app or a future mobile app (see the comment in `.env.example`).
   - `JWT_SECRET` / `SYNC_API_KEY` are auto-generated by Render (`generateValue: true`) — you don't need to set these, but note them down from the dashboard if you ever need to reproduce a `SYNC_API_KEY` value elsewhere.
4. Deploy. First build takes a few minutes (installs deps, builds `@baraka/shared`, runs `prisma migrate deploy`, builds the server). Watch the build log for the Prisma migration step — it should apply cleanly against the empty Supabase database.
5. Once live, note the URL Render gives you (`https://barakapos-server.onrender.com` or similar) — that's your production server URL.
6. Seed initial data if needed: from your machine, temporarily point `server/.env`'s `DATABASE_URL` at the Supabase string and run `pnpm --filter server db:seed` (or connect via `psql`/Supabase's SQL editor and insert your real store/admin user directly — the seed script creates dev/demo data you may not want in production).

## 4. GitHub Actions — keep-alive

1. In your GitHub repo: **Settings > Secrets and variables > Actions > Variables** tab.
2. Add a repository variable `RENDER_HEALTH_URL` = `https://<your-render-service>.onrender.com/api/health`.
3. The workflow (`.github/workflows/keep-alive.yml`) runs automatically every 10 minutes, 06:00–22:00 UTC — adjust the cron expression to your store's actual open hours/timezone (UTC-based) to avoid unnecessary pings overnight.

## Known limitation to accept or budget for

Render's free tier sleeps after 15 minutes with no incoming requests, and **a sleep drops any open Socket.io connections** — so real-time stock/sale updates between terminals can silently stop working for whoever's connected when it sleeps, until they reconnect on their next action. The keep-alive ping keeps it awake during the hours you configure, but if you need guaranteed always-on sockets outside those hours (e.g. a 24-hour store), the fix is Render's cheapest paid plan (a few dollars/month) — there's no way to get a truly persistent, never-sleeping process for $0 anywhere.

## Desktop app distribution (already configured)

`client/package.json` and `client/electron-builder.office.json` already publish releases via `electron-updater` to GitHub Releases (free) — but currently point at placeholder values:

```json
"publish": { "provider": "github", "owner": "baraka", "repo": "baraka-pos-releases" }
```

Update `owner`/`repo` in both files to your real GitHub org/repo before running `electron-builder`'s publish step, so auto-update actually finds releases.

## Mobile app (once built, per the mobile plan)

- **Building**: EAS Build free tier (30 builds/month: 15 iOS + 15 Android) — no cost.
- **Distributing to real users via app stores**: not free — Apple Developer Program is $99/year, Google Play is a $25 one-time registration fee. This is Apple/Google's fee, not a hosting cost, and there's no free alternative for official store listings.
